Welche der folgenden Kommentar-Syntaxen ist in PHP nicht gültig?

A// Einzeiliger Kommentar
B# Einzeiliger Kommentar
C

✓ Richtig. <!-- --> ist HTML-Kommentar-Syntax, kein PHP. In PHP: // und # für einzeilig, /* */ für mehrzeilig.
✗ Falsch. <!-- --> ist HTML, nicht PHP. PHP kennt: // (einzeilig), # (einzeilig) und /* */ (mehrzeilig/Block).

A3Multiple Choice1 Punkt

Warum sollte am Ende einer PHP-Datei, die Sessions oder Header verwendet, der schliessende ?>-Tag weggelassen werden?

AWeil PHP sonst die Datei als HTML interpretiert
BWeil nach ?> ein Zeilenumbruch als Ausgabe gesendet wird, was «Headers already sent» verursacht
CWeil ?> in modernem PHP veraltet ist
DEs gibt keinen Grund, ?> wegzulassen
✓ Richtig. Nach ?> folgt oft ein unsichtbarer Zeilenumbruch. Dieser wird als HTTP-Ausgabe gesendet, bevor session_start() oder header() aufgerufen wird — Fehler!
✗ Falsch. Richtig ist B. Der schliessende PHP-Tag gefolgt von einem Zeilenumbruch sendet diesen als Ausgabe zum Browser. Das verhindert dann den Aufruf von session_start() und header().

Das Buchantiquariat hat zwei Formulare: ein Suchformular (Bücher nach Autor suchen) und ein Login-Formular. Welche Methoden-Kombinaton ist korrekt?

ASuche: POST · Login: GET
BSuche: GET · Login: POST
CBeide: POST

✓ Richtig. GET für Suche: URL ist teilbar, bookmarkbar, kein Sicherheitsproblem. POST für Login: Passwort darf nie in der URL erscheinen (Browser-Verlauf, Server-Logs).

Was ist der Unterschied zwischen $_GET und $_POST bei der Datenübertragung?

AGET ist schneller, POST ist langsamer
BGET ist für grosse Datenmengen, POST für kleine

C2Multiple Choice2 Punkte

Was ist Session Hijacking und wie wird es verhindert?

AAngreifer stiehlt die Session-ID eines eingeloggten Benutzers und gibt sich als dieser aus. Schutz: HTTPS + session_regenerate_id() + HttpOnly-Cookies
BAngreifer errät das Passwort durch Brute-Force. Schutz: starke Passwörter
CAngreifer injiziert SQL-Code in die Datenbank. Schutz: Prepared Statements
DAngreifer löscht die Session-Datei auf dem Server. Schutz: Backups
✓ Richtig. Session Hijacking = Diebstahl der Session-ID (z.B. via XSS, unsicheres WLAN). Mit der gestohlenen ID kann der Angreifer die Session des Opfers übernehmen. HTTPS verschlüsselt die Übertragung, session_regenerate_id() erzeugt nach Login eine neue ID.
✗ Falsch. Richtig ist A. Session Hijacking ist der Diebstahl der Session-ID, nicht ein Passwort-Angriff oder SQL-Injection. Schutz: HTTPS (verschlüsselt ID-Übertragung) + session_regenerate_id() + HttpOnly-Flag auf dem Session-Cookie.

D1Multiple Choice2 Punkte

Ein neuer Administrator wird im System registriert. Der folgende Code speichert das Passwort. Was ist falsch?

1$pw = $_POST['password'];
2$hash = md5($pw);
3// $hash in DB speichern
Amd5() ist korrekt, man muss nur einen Salt hinzufügen
BDas Passwort sollte mit base64_encode() gespeichert werden
Cmd5() ist für Passwörter viel zu schnell und unsicher. Korrekt: password_hash($pw, PASSWORD_DEFAULT)
DEs fehlt nur htmlspecialchars() vor dem Hashen
✓ Richtig. MD5 kann Milliarden Hashes pro Sekunde berechnen — mit Rainbow-Tables ist ein MD5-Hash in Sekunden geknackt. password_hash() verwendet bcrypt, das absichtlich langsam ist und automatisch einen zufälligen Salt hinzufügt.
✗ Falsch. Richtig ist C. MD5 ist kryptografisch gebrochen und für Passwörter komplett ungeeignet — auch mit Salt. base64 ist nur Kodierung, kein Schutz. Nur password_hash($pw, PASSWORD_DEFAULT) verwenden!

Was bedeuten die Teile des bcrypt-Hashes $2y$10$abc...xyz?

A$2y$ = Version 2, $10$ = Passwort-Länge, Rest = Hash

E1Multiple Choice2 Punkte

Warum verhindern Prepared Statements SQL-Injection, der folgende direkte Code jedoch nicht?

// Direkt (UNSICHER):
$sql = "SELECT * FROM buecher WHERE autor = '$autor'";
// Prepared (SICHER):
$stmt = $db->prepare("SELECT * FROM buecher WHERE autor = ?");
$stmt->bind_param("s", $autor);
APrepared Statements sind schneller, weshalb weniger Zeit für Angriffe bleibt
BBei Prepared Statements wird der Benutzerwert automatisch in Grossbuchstaben umgewandelt
CSQL-Struktur und Benutzerdaten werden getrennt zum Server gesendet. Der Benutzerwert wird nie als SQL-Code interpretiert
DPrepared Statements verschlüsseln die Abfrage vor dem Senden
✓ Richtig. Das ist der Kern: Bei prepare() wird der SQL-String mit Platzhaltern (?) an den Server gesendet und dort kompiliert. Danach werden die Werte separat übertragen — sie können nie als SQL-Befehle ausgeführt werden.
✗ Falsch. Richtig ist C. Der entscheidende Unterschied: SQL-Befehl und Daten werden getrennt übertragen. Die Datenbank behandelt bind_param-Werte immer als reinen Text/Daten, nie als SQL-Syntax.

Ein Kunde gibt im Kommentarfeld ein: <script>alert('XSS')</script>. Welche Funktion verhindert die Ausführung dieses Codes beim Anzeigen?

Ahtmlspecialchars($kommentar) – wandelt < > in &lt; &gt; um, Browser führt es nicht aus

✓ Richtig. htmlspecialchars() ist die korrekte Funktion zum Anzeigen von Benutzerdaten. Es wandelt < in &lt; um — der Browser zeigt es als Text an, führt es nicht als Code aus. strip_tags() wäre auch möglich, entfernt aber Tags komplett statt sie anzuzeigen.

AHTTPS ist schneller, weshalb es für Login-Formulare bevorzugt wird
